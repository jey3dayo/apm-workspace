# Ship

互換のための名前だけのエイリアス。出荷の手順そのものは委譲先が持つ。慣れたら `full-stop` / `full-send` を直接使う前提で、この名前は将来廃止する方向。

## 1. 委譲先を決める

| 呼ばれ方・依頼                                     | 委譲先      | 終点                     |
| -------------------------------------------------- | ----------- | ------------------------ |
| `ship` / `ship pr` / 「PR まで出して」「出荷して」 | `full-stop` | PR を ready で渡すまで   |
| `ship merge` / 「マージまで」                      | `full-send` | マージまで（§2 の gate） |

引数も終点の指定も無い `ship` は `ship pr` として扱う。マージは、依頼にマージが含まれるときだけ委譲先に含める。

委譲先の起動前に §2 の上書きを読み、委譲先の手順へ組み込む。委譲先が参照するスキルのうち、この workspace に入っていないもの（`leaving-pr-comments`）への参照は §2(c) に読み替える。

- 完了条件: 委譲先と終点を1行で言える

## 2. 上書き

委譲先の既定より、次を優先する。

### (a) polish を前段で呼ぶ

委譲先が変更を仕上げる前に `polish` を呼ぶ（base-ref、自分の変更ファイル、変更の意図を引数で渡す）。PR で追加・変更したコードコメントが長く・過剰になる傾向があるため、コメントの圧縮も polish の仕事として含める。削除候補は委譲先ではなく親が判断する。polish が差分を書き換えたら、委譲先の gate はそこから回し直す。

### (b) マージ gate は厳しい方を優先する

`full-send` の自律マージの既定より、`t3-stack` の gate を優先する。

- ワーカーはマージしない
- 担当 bot がマージしてよいのは、人間の常設許可か、そのタスクでの条件付き許可があり、かつ上位 tier のレビュー承認で blocking が 0、レビューコメント（bot のレビューを含む）をすべて確認済み、CI が緑、merge state が CLEAN のときだけ
- `--admin` は使わない

### (c) PR コメントの正本

- コメントの取得は `gh-address-comments`
- 返信と resolve は `pr-followup`（仕分け、推敲、bot の修正済みスレッドだけ resolve、人間のスレッドは resolve しない、を含む）

### (d) レビューは sol-loop、heavy 時は council

委譲先のレビュー工程は `sol-loop` で行う。変更が heavy（ファイル数・行数が大きい、削除を含む、配布・権限・認証・セキュリティ境界に触れる）なときは `council` に上げる。

## 3. 落とした終点

旧 ship の commit だけ・push だけの終点は持たない。commit だけなら `atomic-commit` を使う。

## 4. 報告

委譲先の報告に、§2 の上書きのうち実際に効いたものを添える。止まった場合は、委譲先の報告形式のまま、再開に要る判断を1行で書く。
