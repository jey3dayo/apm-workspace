# Learning Intake

セッションで踏んだ失敗を、次回の振る舞いを変える1箇所の編集に変換する。環境の弱点を広く洗い出す診断は `/retro`（mattpocock/skills）が担い、本スキルはその候補やセッションの失敗を owner へ反映する側を受け持つ。

**既定の結果は `保留` であって編集ではない。** 根拠と owner が揃ったものだけが `applied` になる。回避策をその場で消費して終わると、同じ穴を全リポジトリで踏み直す。

## 経路を先に決める

起動の仕方で、どこから入りどこで終わるかが変わる。

| 経路                                  | 実行する範囲                                                                                                                                                                                                                      | 終了条件                                                                                                                                    |
| ------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| local: owner が今回の許可範囲内にある | 同じセッションが §1 → §2 → §2b → §3 → §4 を通す（§2a は受入れ経路専用の観測検証なので飛ばす）                                                                                                                                     | 適用と検証まで                                                                                                                              |
| 報告: owner が許可範囲の外にある      | §1 で観測・参照 artifact・適用範囲をまとめ、§2 で owner 候補を判定し、§5 の書式で drop box にファイルを置く                                                                                                                       | drop box に置いた path を報告する、または §5 の fallback 時は置いた絶対パスと依頼文をユーザーへ返したところまで。`applied` ではなく報告完了 |
| 受入れ: 報告を受け取った側            | `~/.apm/tmp/learning-intake/` を一覧し、ユーザーが別の path を渡したらそれも対象にする。1ファイルずつ §2 で owner 候補 → §2a で報告の観測を検証（検証できた観測で §1 の台帳採点も行う） → §2b で4点を確認 → §3 → §4 → §5 の片付け | 適用と検証、§5 の片付けまで                                                                                                                 |

`~/.apm` で引数なしに呼ばれ、drop box に未処理があるときは、受入れ経路を既定にする。

**owner（変更の正本）と報告先（宛先）は別物である。** 報告経路でも owner 候補は判定するが、確定するのは受入れ側。「別 repo だから APM を直せない」と決めつけない——所有・今回の許可範囲・OS 権限は別の話で、明示的に許可された cross-repo 変更なら local 経路になる。

## 1. 学びを取り出す

入力は次の2つのどちらか。

- `/retro` の改善候補。広い診断が要るなら先に `/retro` を回してもらう
- セッションで踏んだ失敗・ユーザーの訂正（言われた言葉そのもの）・2回以上出た回避策・文書と実装の食い違い・効いた点

**根拠は解釈でなく事実で書く。** エラー文、ユーザーの発言、コマンドの出力。`/retro` の候補も、セッションログ・ファイル・コマンド出力の実物を引用できたものだけを拾う。「〜が不安定だった」のような印象は根拠にならない。

スキルの不具合を主張する前に、そのスキルの現物を読んで契約を確認する。

**取り出す前に、台帳 `~/.apm/docs/learning-ledger.md` を採点する。** 判定が `効いた` / `対応済み` 以外の行のうち、今回のセッションや入力で確認方法の信号が見えるものを `効いた` / `一部` / `効かなかった` / `未検証` で採点し、判定の根拠（件数・出力・発言）を同じ行に書く。`効かなかった` 行は、その変更を owner から外すか、より強い形（lint など）に作り直す案を学びとして §2 以降へ通す。外す・作り直すが済んだら判定を `対応済み` に書き換え、結果を根拠に追記する（作り直した変更は §4 で新しい行になる）。台帳に書き込めない経路では、採点結果を報告に含める。

完了条件: 台帳の採点できる行に判定と根拠が付き、各項目に入力元と引用できる根拠が付いている。

## 2. owner を1つ名指しする

1項目につき owner はちょうど1つ。2つに書くと、片方が古くなったとき現状を復元できなくなる。

| 学びの性質                                                                                  | owner                                                                                        | 適用の正本                        |
| ------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- | --------------------------------- |
| その repo だけに効く、機械的に検出できる違反（固定パターン・禁止 API・import 形・配置規則） | 当該 repo の lint 設定 / lefthook / CI。本スキルは `todo.txt`（無ければ issue）への起票まで  | `orchestrator-worker`             |
| catalog skill の契約破れ・手順の摩擦・実装との食い違い                                      | `catalog/.apm/skills/<name>/`                                                                | `apm-usage` → `apm-deploy-verify` |
| 全リポジトリに効く規範・禁止事項・判断基準                                                  | `~/.apm/catalog/AGENTS.md`                                                                   | `apm-usage`                       |
| owner が今回の許可範囲の外にある（報告経路）                                                | APM 側が owner 候補の行 + drop box `~/.apm/tmp/learning-intake/`                             | 本スキル §5                       |
| そのリポジトリだけの規約・構成                                                              | 当該 repo の `AGENTS.md` / `CLAUDE.md`                                                       | `docs-review`                     |
| そのリポジトリだけの、レビュー時に判断する規約                                              | 当該 repo の `.claude/review-guidelines.md`（`code-reviewer` / `github-pr-reviewer` が読む） | 本スキル §4                       |
| コード・スクリプトの不具合                                                                  | 当該 repo の `todo.txt`（無ければ issue）。本スキルは起票まで                                | `orchestrator-worker`             |

lint / hook / CI の行と「コード・スクリプトの不具合」の行は、owner が今回の許可範囲内にあるときだけ使う。範囲外（別 repo から見た `~/.apm/scripts` など）は報告経路の行に当て、受入れ側が owner 側の `todo.txt` へ起票する。

機械的に検出できる違反は、規約文の行より lint / hook / CI の行を先に選ぶ。全リポジトリ向けの規範は `~/.apm/catalog/AGENTS.md` の行に置き、各 repo での lint 化は個別に起票する。`/retro` が提案する `CODING_STANDARDS.md` は作らず、この表の行へ読み替える。

ユーザー訂正は行き先が割れるので、次で判別する。

- 全リポジトリで守るべきルールになるもの → `~/.apm/catalog/AGENTS.md`（`~/.claude/CLAUDE.md` はその配布先であって正本ではない）
- この環境についての事実（一度きりだが忘れると再度踏む） → ネイティブの memory 機構へ渡し、本スキルでは扱わない

owner が決まらない、または根拠が弱い項目は `保留` にして、何が足りないかを名指しする。憶測で owner を埋めない。

local 経路で `保留` にした項目のうち、owner 候補が APM 側（catalog skill・`~/.apm/catalog/AGENTS.md`・`~/.apm` のスクリプト）のものは、セッションが終わると消えるため、§5 の報告ファイル書式で `status: 未処理` として置き、保留理由は `不足:` 項目に書いて drop box `~/.apm/tmp/learning-intake/` に置く。当該 repo 側が owner 候補のものは報告に残すだけでよい。

完了条件: 各項目が `applied` 候補（owner 1つ）か `保留`（不足を明記）のどちらかに分かれている。

## 2a. 受入れ経路では、報告の観測を検証する

報告で受け取ったものは**「送信側がそう観測したという報告」**であって、確定した事実ではない。観測報告・因果の推定・推奨を分けて扱う。送信側が主体を断定していても、それを自分で観測し直すまでは仮説として扱う。セッションログの呼び出し回数や遵守率を確かめるときは、[references/session-log.md](references/session-log.md) の手順で数える。

完了条件: §2b へ渡す各行について、報告のまま採った部分と、受入れ側が独立に確認した事実が区別されている。

## 2b. 適用前に4点を確認する（local / 受入れ共通）

1回のセッションで拾った学びも、他セッションからの報告も、`applied` として §3 へ上げる前に同じ4点を通す。**採否を左右する主張だけを、使用中 version の一次情報と既存規約へ照合する。** 全部の実測を再現する必要はない。確認できない前提に採否が依存する項目は `保留` に戻す。

**最初に、この学びが無くても困らないかを問う。** 「この学びが消えたら、最終的なコード・テスト・既存文書を読んだ次のエージェントが同じ失敗をするか、大きな再調査をするか」。しないなら記録せず、不採用として理由を報告する。作業が完了したこと、労力がかかったこと、diff が大きいことは採用理由にならない。

この問いを通った項目だけ、次の 4 点を確認する。

- その主張が観測から本当に導けるか（1 回の実行状態から恒常的な契約を導いていないか）
- 適用範囲（対象の path・root・version・条件を取り違えていないか。集計や件数そのものが誤っていることもある）
- 反例（その規則が誤りを招くケース）
- 既存記述との重複（同じ意味が既にどこかにあるか。見つけた場合の統合の仕方は §3 が正本）

完了条件: 最初の問いで落とした項目とその理由、および §3 へ上げる各行について4点を確認した結果が示されている。

## 3. 提案してから書く

`applied` 候補が0件のときは、表を作らず `保留` の一覧と何が足りないかを報告して終了する。owner は編集しない（§2 の保留の退避は行う）。受入れ経路では、終了前に §5 の片付けを行う。

`applied` 候補があるときは、ユーザーへ出す表を「やること」だけにする。当該学びと owner への適用をユーザーが明示的に選択済みなら再確認せず §4 へ進む。分析・提案のみ、または適用対象が未特定なら確認を待つ。保留は編集せず、不足をユーザーだけが補えて継続に必要な場合だけ質問する。

| 学び     | owner           | 次回の振る舞い     |
| -------- | --------------- | ------------------ |
| `<一行>` | `<ファイル1つ>` | `<次回どう動くか>` |

根拠（エラー実物 / 発言 / 出力）と確認方法（何を見れば変わったと言えるか）は、行ごとに手元で埋める。確認方法は §4 で台帳に書く。ユーザーへ見せるのは、求められたときだけにする。保留と不採用は表にせず、1行ずつ理由を添える。

「次回の振る舞い」は、今回何が起きたかではなく**次回どう動くか**で書く。書けないものは学びとして成立していないので `保留` へ戻す。

既存の関連記述を正本としてその箇所へ統合し、別箇所に並立させない。誤りなら置換し、不完全なら同じ箇所を補強する。

完了条件: 0件なら保留と不足の報告で終わっている。候補があるときは、全行の根拠と確認方法が手元で埋まり、ユーザーが表（学び・owner・次回の振る舞い）から適用対象を選んでいる。

## 4. 適用して検証する

選ばれた行だけを書く。文体・粒度・構造は owner 側の既存記述に合わせる。

- catalog skill / CLAUDE.md の編集と再配布は `apm-usage` の判定に従い、検証は `apm-deploy-verify` へ渡す
- `applied` にした行は、`~/.apm/docs/learning-ledger.md` の表へ1行ずつ追記する（日付・学び・owner・§3 の確認方法・判定 `未計測`）。台帳は次回 §1 で採点する変更の一覧であって、memory ではない。`~/.apm` に書き込めないときは、追記する行を報告に含め、ユーザーへ `~/.apm` での追記を依頼する

報告には、`applied` にした行と、`保留` にした行および何が足りなかったかを両方書く。

完了条件: 適用した各行について、owner のどこが変わったかと検証の結果を示し、台帳に行が追記されている（書き込めないときは追記する行を報告している）。報告の末尾に、次にやること（未コミットの変更があれば `/atomic-commit`、保留の再開条件、`doctor:intake` の滞留）を1〜2行で添えている。

## 5. 報告ファイル書式

- ファイル名書式: `<YYYYMMDD-HHMM>-<slug>.md`
- 報告ファイルの必須項目: 日付、送信元 repo、§1 の入力元と根拠の実物、適用範囲、§2 の owner 候補、`status`（`未処理` / `保留`）。保留理由があるときは `不足:` に書く。セッションの挙動に関する報告は、該当セッションの ID（`~/.claude/projects/<dir>/<id>.jsonl` の `<id>`）も書く
- `status` 行の書式: 行頭から `status: 未処理` または `status: 保留` だけを書き、後ろに文字を付けない（理由は `不足:` へ書く）。リスト記号や強調を付けない。`status: 保留` の行が無いファイルは未処理として扱う（doctor もこの規則で数える）
- 受入れ後の片付け（`status: 保留` に遷移できるのは受入れ側だけ）:
  - `applied` → §4 で台帳に追記したことを確かめてから、ファイルを削除する
  - 不採用 → ファイルを削除し、判断は `~/.apm/done.txt` に記録する
  - `保留` → `status: 未処理` の行を `status: 保留` に書き換え、`不足:` を追記して残す
- 書き込みを拒まれた場合（sandbox など）: 自 repo の `tmp/learning-intake/` に置き、ユーザーへ「`~/.apm` のセッションで learning-intake を使い `<置いたファイルの絶対パス>` を取り込んで」と依頼する文を返す
- ユーザーが渡した `~/.apm` 外の報告は、受入れ開始時に `~/.apm/tmp/learning-intake/` へ移してから処理する（片付けと doctor の集計を drop box に一本化するため）
