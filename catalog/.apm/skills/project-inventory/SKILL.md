# Project Inventory

プロジェクトを一度見渡す棚卸しの束ね役。トラックの出どころは Vox（@Voxyz_ai）の6プロンプト集のスレッド（https://x.com/Voxyz_ai/status/2122011755240984607）。全部を機械的に回すのではなく、**対象プロジェクトと依頼の文脈を見て、効くものを選んでから呼ぶ**。選ばなかったものは、報告に「見送り」として理由と一緒に残す。

## トラック候補（6プロンプト）

1. The State Machine Hunter — 状態まわりの総点検。subagent が `state-machine-audit` の手順を流用して回す。状態管理が複雑なアプリ、状態起因っぽい不具合があるときに特に効く。
2. The Open-Source Scout — 未知の機能を作る前に OSS を探して方針を比べる。棚卸しというより着手前の型なので、棚卸し中に「これから作るもの」の相談が混ざったときだけ拾う。
3. The Bug Triager — バグを頻度×深刻度（各1〜10）で採点する。積が閾値（既定5）未満なら issue 化候補として報告に載せるに留め、コードには触らない。閾値以上なら優先して直す候補として報告する。誰も頼んでいない稀な・将来のケースのために設計しない。open issue や既知バグが溜まっているときに拾う。閾値はプロジェクトに合わせて調整する。
4. The Closer — 仕事を最後まで終わらせる／削除前に聞く／最後に要点を平易な言葉で recap する、という進め方の型。監査トラックではないので、棚卸し全体の実施スタイルとして常に適用する（選ぶ／選ばないの対象外）。
5. The CI Auditor — `gh` で直近150回の CI runs を取り、各ジョブの時間を「キュー待ち／setup（checkout・依存インストール・キャッシュ復元）／実行」に分解して、遅いジョブ上位5件を各パートの秒数内訳付きで出す。報告のみで変更はしない。CI が遅い・不安定という自覚があるときに拾う。
6. The Rebuilder — 「今日ゼロから同じ目的で作り直すなら、何を残す必要があるか」。残すもの／捨てるものの線引きが要るとき、または棚卸しの締めのレンズとして拾う。

## 手順

1. 範囲確定：対象リポジトリと対象コミットを固定する。リポの `AGENTS.md` / `CLAUDE.md` を先に読む。
2. 選定：トラック候補から今回回すものを選ぶ（The Closer は常時適用なので選定対象外）。判断材料は、引数で渡された文脈と、リポから読める近況（直近の issue・PR・CI の様子）に限る（fork は会話履歴を見られない）。前回の棚卸し報告書がリポ内または指定先に残っていれば、それも材料にする。選定理由は報告書の冒頭に書く。
3. 実行：選んだトラックごとに subagent を立てて並列で回す。各 subagent は読み取り専用で、自分のトラックの報告書だけを返して終わる（Bug Triager は issue 化せず、候補として報告に載せるところまで）。状態トラックの subagent は `state-machine-audit` の手順そのままで行う。
4. 統合報告：呼び出し側が各 subagent の報告書を受け取り、トラック別の要約＋横断の優先順位（最初にやるべき順）に畳む。見送ったトラックと理由も残す。取得できなかった計測（権限・履歴不足など）は「未計測」として残し、推測で補完しない。報告書のファイル化は親セッションが行う。

## 境界

- 棚卸しは「見る」まで。直し始めない。修正・実装・Issue 化は、報告を受けてから別作業。
- CI の失敗デバッグはこのスキルの外（`gh-fix-ci` の領分）。CI Auditor が扱うのは遅さ・不安定さの計測だけ。
- 汎用のコードベース監査・改善計画（`improve` 等）とは別物で、本スキルは Vox の6プロンプトからのトラック選定に限る。
- トラック単体で頼まれたら束ねない（例：状態だけなら `state-machine-audit` を直接使う）。
