# State Machine Audit

元のプロンプト（Vox @Voxyz_ai, "The State Machine Hunter", https://x.com/Voxyz_ai/status/2122011755513561314）：

> "Find all of the implicit state machines in my app. Make the best decision that will elevate all three: the user experience (UX), developer experience (DX), and agent experience (AX) always, without breaking anything."

このプロンプトを再現可能な監査手順に落としたもの。対象アプリのコードを読み取り専用で全量スキャンし、boolean・nullable・文字列値・モジュール変数・タイマー・永続カラム等の組み合わせで実質的に状態遷移を表しているもの（暗黙のステートマシン）を重複なしで同定し、フェーズ分けした改善計画まで出す。実装はしない。実績：jey3dayo/ultra-rss-reader で約60件を同定し Phase 0 まで進めた（同リポの #676〜#678）。

## 手順

### 1. 範囲確定

- 対象リポジトリと対象コミットを固定し、報告書の冒頭に記録する。リポが見つからなければ `ghq list`（シェルの無い環境では ghq ルートの列挙）で探す。
- 対象がコードのリポジトリでない場合（Web アーティファクト、SaaS の設定系、cron 等のジョブ群を含むシステム）は、対象のバージョン／スナップショット取得時刻で固定する。公開アクション・API の説明文が状態仕様（値の意味、保持期間、副作用）を含む場合は、それを一次材料にする。読む材料が変わっても、監査の方法（四方面スキャン・記録項目・判断原則）は変えない。
- 読み取り専用を宣言する：対象リポの状態を変える操作（ファイル作成・変更・checkout・commit 等）はしない。読み取り専用の git コマンド（rev-parse・show・diff 等）は、対象コミットの固定と参照に使う。報告書の返し先は依頼時に決める（既定はその場の回答）。ファイル化を頼まれた場合は、監査する側ではなく呼び出し側（親セッション）が書く。
- 対象リポの `AGENTS.md` / `CLAUDE.md` を先に読む。

### 2. 四方面スキャン

並列で全量を見る（並列で回せない環境では逐次でよい）。①UI 層 ②データ・非同期層 ③ドメイン・ワークフロー層 ④フロー横断（タイマー、リトライ、永続化、外部連携）。

同定の目安：複数の真理値・nullable・文字列リテラルの組み合わせでしか状態を表せていないもの／同じ真実が複数箇所にコピーされているもの／到達不能・脱出不能な状態があるもの。加えて、同一実体に複数のキー系統（安定 ID とタイトル文字列等）が併存し、書き込み経路によって状態レコードが分岐するもの（同一性の二重キー）／開始と結果記録の2点だけで、実行中（in-flight）を表す標識・開始時刻・試行回数がない実行プロトコル（結果未記録と未実行が区別できない）／遷移の判定がコードではなく散文＋LLM の分類に委ねられ、文言次第で状態が揺れる導出状態機械も対象に含める。

### 3. 各件の記録

場所（ファイルとシンボル）／符号化（何の組み合わせで状態を表しているか）／遷移（何が引き金か）／型で排除できない不正状態／真実の多重化（何重か）／stuck 条件／影響を UX・DX・AX に分けて書く。

AX の定点観点：開発用の再現手段（dev scenario・story・fixture）が到達後の状態しか再現できず、エラー・中間状態を再現できないものは、AX の穴として記録する。

### 4. クラスタ化と判断原則

- 重複を除き、関連する件をクラスタにまとめる（例：同期まわり）。件数とクラスタ地図を報告書の冒頭に置く。
- 判断原則は「何も壊さず、UX・DX・AX の3つすべてを常に向上させる」。
- FSM ライブラリの全面導入はしない。既存の判別共用体など良い型を雛形にする。
- 進める順序は「導出層で明示化 → テストで不変条件固定 → 実状態統合」。DB・同期・永続化など実状態に触るものは最高リスクとして最終フェーズに回す。

### 5. フェーズ計画と報告

- Phase 0 の型：①カタログの docs 化 ②死に状態・未使用機構の整理 ③エラー・中間状態を再現できる再現手段の追加。以後のフェーズはクラスタ単位にリスク昇順で並べる。
- 報告：対象コミット、調査済みの範囲・除外した範囲・未調査の範囲、総件数、クラスタ地図、各件の記録、フェーズ計画。判断に迷った件は「未判定」として根拠と一緒に残す（勝手に潰さない）。

## 境界

- 実装・Issue 化・PR 作成はこのスキルの外。監査結果を受けて次に進むところから別作業。
- 対象の実行環境に制約がある場合（会社リポ等）は、その環境の委譲ルールに従い、監査自体の方法は変えない。
