# PR フォローアップ

自分の PR に付いた指摘に応え、レビュアーへ渡すまで。スレッドの取得と修正は `gh-address-comments` が持つ。ここにあるのは返信・推敲・resolve・引き渡しの規則だけ。repo に PR 本文用のスキルがあれば、本文の作成・更新はそれ経由にする。

ユーザーが指摘への対応・返信を依頼したとき、または `ship` §2 から呼ばれたときの起動は、見えている actionable な指摘をすべて直し、返信し、bot のスレッドを resolve する依頼として扱う。`gh-address-comments` の「どれを直すか確認する」と、返信・resolve の許可は、これで満たされる。確認が要るのは §1 の確認待ちだけ。「指摘を見て」のような読み取りの依頼では、§1 の仕分けを報告して終える。

`ship` §2 から呼ばれたときは、commit と push を `ship` の工程で行い、push の後は CI を待たずに §3〜§4 を行って `ship` の CI 工程へ戻る。§1〜§4 の完了条件を `ship` の次へ進む条件として使い、§2 の確認は `ship` の full gate で行う。確認待ちのスレッドが残るなら `ship` §3 で止める。

## 1. 指摘を仕分ける

`gh-address-comments` で未解決スレッド、会話コメント、レビュー本文を取り、それぞれを次のとおり分ける。

- 指摘者: スレッドのルートコメント、会話コメント、レビュー本文の `author { __typename login }` が `Bot` なら **bot**（Codex、Greptile など）、それ以外（null を含む）は**人間**。`fetch_comments.py` は `login` しか返さないので、`__typename` は GraphQL で別に引く
- 対応: 次の4つ
  - 直す: 見えている指摘（Suggestion、軽微な命名・テストの穴を含む）はこの PR で直す
  - 見送る: 別 PR が担当している指摘と、ユーザーが対象外と決めた指摘だけ
  - 確認待ち: 指摘同士の衝突、振る舞いの退行、曖昧な指摘、仕様変更を伴う指摘。ユーザーに確認し、答えが出るまで返信案の作成で止める
  - 対応不要: 称賛、FYI、重複、現行コードに当てはまらない outdated、resolved 済み、bot の要約コメント・要約レビュー。返信しない

- 完了条件: 全スレッド、会話コメント、レビュー本文に、指摘者の区分と対応が付いた

## 2. 直す

修正は新しい commit として積み、force push しない（squash merge で畳まれる）。変更範囲に応じた確認（テスト・lint・typecheck）を実行する。

- 完了条件: 修正を push し、実行したコマンドと結果を返信に書ける

## 3. 返す

人間の指摘にも bot の指摘にも返信する（「直す」と「見送る」が対象）。直したスレッドへは push 直後に、対処内容・SHA・検証結果を書く。見送るスレッドへは、判断と理由を書く。返信先は GitHub 上のスレッドと会話コメントで、会話コメントとレビュー本文での指摘には会話コメントで返す。

- スレッドへの返信: GraphQL `addPullRequestReviewThreadReply`
- 内容が変わったとき: 新しいコメントを足さず、既存のコメントを `updatePullRequestReviewComment`（スレッド返信）か `updateIssueComment`（会話コメント）で編集して、「いまの確定内容」だけの1本に保つ

- 完了条件: 最終 push の後、確認待ちと対応不要を除く各スレッドの最終コメントが自分のものである（会話コメントとレビュー本文での指摘は、その後に自分の返信がある）

### 推敲してから投稿する

GitHub へ出す文面（スレッド返信、PR 本文、PR コメント、issue 本文）は、投稿の前に推敲する。

- 本文を新しく書く段階: issue / PR 本文の下書きは、repo の PR 本文用スキルがあればそれ、無ければ `natural-japanese` の write で作る。スレッド返信はこの段階を省く
- 推敲の段階: global AGENTS.md「コミュニケーション原則」の推敲チェーン（`explain-before-shorten` → `yomiyasu`）だけを、下書きに1回通す。1行のスレッド返信にも適用し、複数の返信は1つの下書きにまとめてよい。書き換えを担うスキルを重ねると指示が食い違うので、`natural-japanese` はこの段階で使わない

推敲は文面を整える作業で、SHA・コマンド・数値・ファイル名は元のまま残す。

- 完了条件: 投稿した文面は推敲を通した版で、SHA・コマンド・数値・ファイル名が推敲前と一致する

### 投稿の範囲

| 宛先                                                           | 扱い                                                   |
| -------------------------------------------------------------- | ------------------------------------------------------ |
| PR のスレッド返信・会話コメント・PR 本文                       | 推敲して投稿する                                       |
| issue（PR の会話コメントを除く）の本文・コメント、Slack の返信 | 推敲した下書きをチャットに出して終える。投稿はユーザー |

## 4. resolve

| 指摘者                          | 操作                                                           |
| ------------------------------- | -------------------------------------------------------------- |
| bot（修正して返信したスレッド） | 修正・push・返信のあとに `resolveReviewThread` で resolve する |
| bot（見送ったスレッド）         | 返信で止め、open のまま残す                                    |
| 人間                            | 返信で止め、open のまま残す                                    |

resolve は「指摘が解消した」という指摘者の判断を表す。人間には判断を委ねる相手がいるので返信で止め、委ねる相手がいない bot の、修正済みのスレッドだけを作成者が resolve する。人間のスレッドの resolve をユーザーが明示指示した場合は、この理由を伝えてから確認する。

報告には「人間のスレッドは未解決のまま。対応漏れではない」と添える。

- 完了条件: 修正して返信した bot のスレッドが全部 resolved で、それ以外のスレッドの状態が変わっていない

## 5. マージ前の確認

ユーザーがマージを依頼したら、`gh pr merge` の前に必ず行う。`ship` の後や CI の完了後に bot のレビューが届くことがあり、`ship` 内の工程だけでは拾えない。

1. §1 と同じ方法で、その時点の未解決スレッド、会話コメント、レビュー本文を取り直す
2. 最終コメントが自分のものでないスレッドと、自分の返信がない会話コメント・レビュー本文での指摘を、§1〜§4 で処理する。この依頼は §1 の起動条件を満たすので、修正・返信・bot の resolve に確認は要らない
3. 修正を push した場合は、CI が pass してから 1 へ戻る
4. 確認待ち（§1）が残るなら、マージせず止めて報告する

修正して push しない（見送りと返信だけの）ときは CI を待たない。

- 完了条件: マージの直前に、未解決スレッドの最終コメントがすべて自分のもので、自分の返信がない指摘が無く、確認待ちが無い

## 6. ready

ユーザーが PR について「ready」と言ったら、draft 解除とレビュアーの assign を行う。PR 番号が無ければ直前の話題の PR を指し、それも無ければ現在のブランチの PR（`gh pr view`）を使う。

1. レビュアーを決める。ユーザーが指定していればそれを使う。指定が無ければ、repo の担当規則（CODEOWNERS、AGENTS.md、メモリ）に従う。規則が無い、または変更が規則に当たらないときは、`gh pr ready` の前にユーザーへ聞く。変更が docs のみのときは、規則があっても PR ごとにユーザーが決めるので、`gh pr ready` の前に毎回聞く
2. 担当が決まったら `gh pr ready <n>` で draft を外し、`gh pr edit <n> --add-reviewer` で足す
3. 報告に、assign した担当と CI の状態を添える

CI が pending でも「ready」の指示を実行する。`--add-reviewer` が失敗したときは、draft が外れた状態のまま、失敗を報告する。

- 完了条件: `gh pr view <n> --json isDraft,reviewRequests` で、`isDraft` が false かつ担当が `reviewRequests` に入っている
