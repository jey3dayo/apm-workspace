# Learning Intake

セッションで踏んだ失敗を、次回の振る舞いを変える1箇所の編集に変換する。

**既定の結果は `保留` であって編集ではない。** 根拠と owner が揃ったものだけが `applied` になる。回避策をその場で消費して終わると、同じ穴を全リポジトリで踏み直す。

## 経路を先に決める

起動の仕方で、どこから入りどこで終わるかが変わる。

| 経路                                  | 実行する範囲                                                                                                                                                                              | 終了条件                                                                                                                                    |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| local: owner が今回の許可範囲内にある | 同じセッションが §1 → §2 → §2b → §3 → §4 を通す（§2a は受入れ経路専用の観測検証なので飛ばす）                                                                                             | 適用と検証まで                                                                                                                              |
| 報告: owner が許可範囲の外にある      | §1 で観測・参照 artifact・適用範囲をまとめ、§2 で owner 候補を判定し、§5 の書式で drop box にファイルを置く                                                                               | drop box に置いた path を報告する、または §5 の fallback 時は置いた絶対パスと依頼文をユーザーへ返したところまで。`applied` ではなく報告完了 |
| 受入れ: 報告を受け取った側            | `~/.apm/tmp/learning-intake/` を一覧し、ユーザーが別の path を渡したらそれも対象にする。1ファイルずつ §2 で owner 候補 → §2a で報告の観測を検証 → §2b で4点を確認 → §3 → §4 → §5 の片付け | 適用と検証まで                                                                                                                              |

**owner（変更の正本）と報告先（宛先）は別物である。** 報告経路でも owner 候補は判定するが、確定するのは受入れ側。「別 repo だから APM を直せない」と決めつけない——所有・今回の許可範囲・OS 権限は別の話で、明示的に許可された cross-repo 変更なら local 経路になる。

## 1. 学びを取り出す

セッションを遡り、次のいずれかに当たるものだけを拾う。

- 手順どおり実行して失敗した箇所（踏んだ経路とエラー実物）
- ユーザーからの訂正（言われた言葉そのもの）
- 2回以上出た回避策
- ドキュメントと実装が食い違っていた箇所
- 効いた点（残す判断の材料になる）

**根拠は解釈でなく事実で書く。** エラー文、ユーザーの発言、コマンドの出力。「〜が不安定だった」のような印象は根拠にならない。

スキルの不具合を主張する前に、そのスキルの現物を読んで契約を確認する。読まずに「壊れている」と書かない。

完了条件: 各項目に、上のどれに当たるかと、引用できる根拠が付いている。

## 2. owner を1つ名指しする

1項目につき owner はちょうど1つ。2つに書くと、片方が古くなったとき現状を復元できなくなる。

| 学びの性質                                             | owner                                                            | 適用の正本                        |
| ------------------------------------------------------ | ---------------------------------------------------------------- | --------------------------------- |
| catalog skill の契約破れ・手順の摩擦・実装との食い違い | `catalog/skills/<name>/`                                         | `apm-usage` → `apm-deploy-verify` |
| 全リポジトリに効く規範・禁止事項・判断基準             | `~/.apm/catalog/AGENTS.md`                                       | `apm-usage`                       |
| owner が今回の許可範囲の外にある（報告経路）           | APM 側が owner 候補の行 + drop box `~/.apm/tmp/learning-intake/` | 本スキル §5                       |
| そのリポジトリだけの規約・構成                         | 当該 repo の `AGENTS.md` / `CLAUDE.md`                           | `docs-review`                     |
| コード・スクリプトの不具合                             | 当該 repo の `todo.txt`（無ければ issue）。本スキルは起票まで    | `orchestrator-worker`             |

「コード・スクリプトの不具合」の行は owner が今回の許可範囲内にあるときだけ使う。範囲外（別 repo から見た `~/.apm/scripts` など）は報告経路の行に当て、受入れ側が owner 側の `todo.txt` へ起票する。

ユーザー訂正は行き先が割れるので、次で判別する。

- 全リポジトリで守るべきルールになるもの → `~/.apm/catalog/AGENTS.md`（`~/.claude/CLAUDE.md` はその配布先であって正本ではない）
- この環境についての事実（一度きりだが忘れると再度踏む） → ネイティブの memory 機構へ渡し、本スキルでは扱わない

owner が決まらない、または根拠が弱い項目は `保留` にして、何が足りないかを名指しする。憶測で owner を埋めない。

local 経路で `保留` にした項目のうち、owner 候補が APM 側（catalog skill・`~/.apm/catalog/AGENTS.md`・`~/.apm` のスクリプト）のものは、セッションが終わると消えるため、§5 の報告ファイル書式で `status: 未処理` として置き、保留理由は `不足:` 項目に書いて drop box `~/.apm/tmp/learning-intake/` に置く。当該 repo 側が owner 候補のものは報告に残すだけでよい。

完了条件: 各項目が `applied` 候補（owner 1つ）か `保留`（不足を明記）のどちらかに分かれている。

## 2a. 受入れ経路では、報告の観測を検証する

報告で受け取ったものは**「送信側がそう観測したという報告」**であって、確定した事実ではない。観測報告・因果の推定・推奨を分けて扱う。送信側が主体を断定していても、それを自分で観測し直すまでは仮説として扱う。

完了条件: §2b へ渡す各行について、報告のまま採った部分と、受入れ側が独立に確認した事実が区別されている。

## 2b. 適用前に4点を確認する（local / 受入れ共通）

1回のセッションで拾った学びも、他セッションからの報告も、`applied` として §3 へ上げる前に同じ4点を通す。**採否を左右する主張だけを、使用中 version の一次情報と既存規約へ照合する。** 全部の実測を再現する必要はない。確認できない前提に採否が依存する項目は `保留` に戻す。

確認するのは次の 4 点。

- その主張が観測から本当に導けるか（1 回の実行状態から恒常的な契約を導いていないか）
- 適用範囲（対象の path・root・version・条件を取り違えていないか。集計や件数そのものが誤っていることもある）
- 反例（その規則が誤りを招くケース）
- 既存記述との重複（同じ意味が既にどこかにあるか。見つけた場合の統合の仕方は §3 が正本）

完了条件: §3 へ上げる各行について、この4点を確認した結果が示されている。

## 3. 提案してから書く

`applied` 候補が0件のときは、表を作らず `保留` の一覧と何が足りないかを報告して終了する。owner は編集しない（§2 の保留の退避は行う）。

`applied` 候補があるときは表にして出す。当該学びと owner への適用をユーザーが明示的に選択済みなら再確認せず §4 へ進む。分析・提案のみ、または適用対象が未特定なら確認を待つ。保留は編集せず、不足をユーザーだけが補えて継続に必要な場合だけ質問する。

| 学び     | 根拠                         | owner           | 次回の振る舞い     | 確認方法                         |
| -------- | ---------------------------- | --------------- | ------------------ | -------------------------------- |
| `<一行>` | `<エラー実物 / 発言 / 出力>` | `<ファイル1つ>` | `<次回どう動くか>` | `<何を見れば変わったと言えるか>` |

「次回の振る舞い」は、今回何が起きたかではなく**次回どう動くか**で書く。書けないものは学びとして成立していないので `保留` へ戻す。

既存の関連記述を正本としてその箇所へ統合し、別箇所に並立させない。誤りなら置換し、不完全なら同じ箇所を補強する。

完了条件: 0件なら保留と不足の報告で終わっている。候補があるときは表の全行が埋まり、ユーザーが適用対象を選んでいる。

## 4. 適用して検証する

選ばれた行だけを書く。文体・粒度・構造は owner 側の既存記述に合わせる。

- catalog skill / CLAUDE.md の編集と再配布は `apm-usage` の判定に従い、検証は `apm-deploy-verify` へ渡す

報告には、`applied` にした行と、`保留` にした行および何が足りなかったかを両方書く。

完了条件: 適用した各行について、owner のどこが変わったかと検証の結果を示している。

## 5. 報告ファイル書式

- ファイル名書式: `<YYYYMMDD-HHMM>-<slug>.md`
- 報告ファイルの必須項目: 日付、送信元 repo、§1 の分類と根拠の実物、適用範囲、§2 の owner 候補、`status`（`未処理` / `保留`）。保留理由があるときは `不足:` に書く
- `status` 行の書式: 行頭に `status: 未処理` または `status: 保留` の1行を書く。`status: 保留` の行が無いファイルは未処理として扱う（doctor もこの規則で数える）
- 受入れ後の片付け（`status: 保留` に遷移できるのは受入れ側だけ）:
  - `applied` と不採用 → ファイルを削除し、判断は `~/.apm/done.txt` に記録する
  - `保留` → `status: 保留` と不足を追記して残す
- 書き込みを拒まれた場合（sandbox など）: 自 repo の `tmp/learning-intake/` に置き、ユーザーへ「`~/.apm` のセッションで learning-intake を使い `<置いたファイルの絶対パス>` を取り込んで」と依頼する文を返す
