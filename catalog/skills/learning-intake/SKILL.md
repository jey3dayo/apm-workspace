# Learning Intake

セッションで踏んだ失敗を、次回の振る舞いを変える1箇所の編集に変換する。

**既定の結果は `保留` であって編集ではない。** 根拠と owner が揃ったものだけが `applied` になる。回避策をその場で消費して終わると、同じ穴を全リポジトリで踏み直す。

## 経路を先に決める

起動の仕方で、どこから入りどこで終わるかが変わる。

| 経路                                  | 実行する範囲                                                                       | 終了条件                                                                 |
| ------------------------------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| local: owner が今回の許可範囲内にある | 同じセッションが §1〜§4 を通す                                                     | 適用と検証まで                                                           |
| 報告: owner が許可範囲の外にある      | §1 で観測・参照 artifact・適用範囲をまとめ、§2 で owner 候補と報告先を判定して送る | NOTIFY の送信成功と task-scoped 登録の片付け。`applied` ではなく報告完了 |
| 受入れ: 報告を受け取った側            | 提供された根拠から入り、検証 → owner 確定 → §3 → §4                                | 適用と検証まで                                                           |

**owner（変更の正本）と報告先（宛先）は別物である。** 報告経路でも owner 候補は判定するが、確定するのは受入れ側。「別 repo だから APM を直せない」と決めつけない——所有・今回の許可範囲・OS 権限は別の話で、明示的に許可された cross-repo 変更なら local 経路になる。transport・envelope・片付けは `agmsg-delegation` が正本で、ここには写さない。

## 1. 学びを取り出す

セッションを遡り、次のいずれかに当たるものだけを拾う。

- 手順どおり実行して失敗した箇所（踏んだ経路とエラー実物）
- ユーザーからの訂正（言われた言葉そのもの）
- 2回以上出た回避策
- ドキュメントと実装が食い違っていた箇所
- 効いた点（残す判断の材料になる）

**根拠は解釈でなく事実で書く。** エラー文、ユーザーの発言、コマンドの出力。「〜が不安定だった」のような印象は根拠にならない。

スキルの不具合を主張する前に、そのスキルの現物を読んで契約を確認する。読まずに「壊れている」と書かない。

完了条件: 各項目に、上のどれに当たるかと、引用できる根拠が付いている。

## 2. owner を1つ名指しする

1項目につき owner はちょうど1つ。2つに書くと、片方が古くなったとき現状を復元できなくなる。

| 学びの性質                                             | owner                                  | 適用の正本                        |
| ------------------------------------------------------ | -------------------------------------- | --------------------------------- |
| catalog skill の契約破れ・手順の摩擦・実装との食い違い | `catalog/skills/<name>/`               | `apm-usage` → `apm-deploy-verify` |
| 全リポジトリに効く規範・禁止事項・判断基準             | `~/.apm/catalog/AGENTS.md`             | `apm-usage`                       |
| owner が今回の許可範囲の外にある（報告経路）           | 上の行の owner 候補 + 宛先 `main-cc`   | `agmsg-delegation`                |
| そのリポジトリだけの規約・構成                         | 当該 repo の `AGENTS.md` / `CLAUDE.md` | `docs-review`                     |

ユーザー訂正は行き先が割れるので、次で判別する。

- 全リポジトリで守るべきルールになるもの → `~/.apm/catalog/AGENTS.md`（`~/.claude/CLAUDE.md` はその配布先であって正本ではない）
- この環境についての事実（一度きりだが忘れると再度踏む） → ネイティブの memory 機構へ渡し、本スキルでは扱わない

owner が決まらない、または根拠が弱い項目は `保留` にして、何が足りないかを名指しする。憶測で owner を埋めない。

完了条件: 各項目が `applied` 候補（owner 1つ）か `保留`（不足を明記）のどちらかに分かれている。

## 2a. 受入れ経路では、提案の前に根拠を検証する

報告で受け取ったものは**「送信側がそう観測したという報告」**であって、確定した事実ではない。観測報告・因果の推定・推奨を分けて扱う。

**採否を左右する主張だけを、使用中 version の一次情報と既存規約へ照合してから §3 へ上げる。** 全部の実測を再現する必要はない。確認できない前提に採否が依存する項目は `保留` にする。

確認するのは次の 4 点。

- その主張が観測から本当に導けるか（1 回の実行状態から恒常的な契約を導いていないか）
- 適用範囲（対象の path・root・version・条件を取り違えていないか。集計や件数そのものが誤っていることもある）
- 反例（その規則が誤りを招くケース）
- 既存記述との重複（同じ意味が既にどこかにあるなら、追記でなくそこを書き換える）

完了条件: §3 へ上げる各行について、独立に確認した事実と、報告のまま採った部分が区別されている。

## 3. 提案してから書く

`applied` 候補を表にして出し、確認を待つ。

| 学び     | 根拠                         | owner           | 次回の振る舞い     | 確認方法                         |
| -------- | ---------------------------- | --------------- | ------------------ | -------------------------------- |
| `<一行>` | `<エラー実物 / 発言 / 出力>` | `<ファイル1つ>` | `<次回どう動くか>` | `<何を見れば変わったと言えるか>` |

「次回の振る舞い」は、今回何が起きたかではなく**次回どう動くか**で書く。書けないものは学びとして成立していないので `保留` へ戻す。

owner に既存の関連記述があるときは、**追記ではなくその箇所を書き換える**。同じ意味が2箇所に増えると、両方を読み合わせないと現状が分からなくなる。

完了条件: 表の全行が埋まり、ユーザーが適用対象を選んでいる。

## 4. 適用して検証する

選ばれた行だけを書く。文体・粒度・構造は owner 側の既存記述に合わせる。

- catalog skill / CLAUDE.md の編集と再配布は `apm-usage` の判定に従い、検証は `apm-deploy-verify` へ渡す
- agmsg NOTIFY の envelope 書式（`source_role` / `target_role` / `task_id` / `report_contract`）は `agmsg-delegation` が正本。返信は来ないので待たない

報告には、`applied` にした行と、`保留` にした行および何が足りなかったかを両方書く。

完了条件: 適用した各行について、owner のどこが変わったかと検証の結果を示している。
