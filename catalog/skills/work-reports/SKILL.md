# Work Reports (MBO GEPPO)

成果報告リポジトリ `~/src/github.com/jey3dayo/work-reports` を管理する。**projects/ が正本、monthly/ は生成物**。

## リポジトリ構成

| パス                   | 役割                                                     |
| ---------------------- | -------------------------------------------------------- |
| `goals/<半期>.md`      | 半期目標（成果目標・ミッション目標）の原文と評価スケール |
| `projects/<id>.md`     | プロジェクト別の中間メモ（正本）                         |
| `inbox.md`             | プロジェクト未分類のクイックメモ                         |
| `monthly/<YYYY-MM>.md` | 月次まとめ。GEPPO 提出文と提出した天気評価を記録         |

## ワークフロー

### 1. 中間メモの追記（随時）

ユーザーが「〜やった」「メモしておいて」と成果を伝えたとき:

1. 該当する `projects/<id>.md` を探す。なければファイル名を提案して新規作成する（見出しに半期目標との関連を明記する）
2. 当月の `## YYYY-MM` セクションに箇条書きで追記する。1エントリは「やったこと + 成果（リリース / PR / 数値）」を1〜2行で
3. どのプロジェクトか判断できない場合のみ `inbox.md` に日付付きで置く
4. 将来の作業は各プロジェクトの `## 今後の予定` に置き、完了したら当月セクションへ移す

### 2. 月次まとめの生成（月末〜月初）

「今月のまとめ」「月報作って」と言われたとき:

1. 前月（必要なら前々月）の `monthly/<YYYY-MM>.md` を読んで叩き台にする。 ユーザーの指示がなくても必ず行う。プロジェクトの見出し名・粒度・並び順を引き継ぎ、前月からの継続案件は「何が進んだか」の差分で書く。前月の `# 今後の予定` は当月の実績になっているか照合する
2. `projects/*.md` と `inbox.md` から当月分を収集する。inbox の項目は projects/ へ振り分けてから使う
3. 証跡を集める。`projects/` の記載は薄いことが多いので、機械的な洗い出しを必ず行う:
   - `ghq list -p` でローカルリポジトリを列挙し、各所で `git log --since=<当月1日> --until=<翌月1日> --author=<自分>` を回して当月コミットのあるリポジトリを特定する（`projects/` に無いリポジトリが出てきたら成果の取りこぼし）
   - 各リポジトリの `tmp/work-log/work-history.md` や本リポジトリの `work-log/<YYYY-MM>/work-history.md`（work-log-maintenance の成果物）があれば、テーマ・期間・要約を流用する
   - 調査対象が複数リポジトリに散る場合は Worker へ並列委譲する（`orchestrator-worker` スキル）
   - 集めた結果を提示し、漏れがないかユーザーに確認する
4. ミッション目標（LT・ハンズオン・スキル展開）は**半期分を遡って集約する**。当月分だけでは進捗評価の根拠にならないため、`projects/` の過去月セクションと過去の `monthly/` を半期の頭まで読む
5. `monthly/<YYYY-MM>.md` を作成する。含める内容:
   - 提出した評価テーブル（①成果 / ②ミッション / ③総合、S〜D。提出前は未記入で作る）
   - GEPPO ④ 提出文（下記フォーマット）
6. 生成後、提出文をコードブロックで提示してコピーできるようにする

### 3. 提出結果の記録

GEPPO 提出後に評価（天気 S〜D）を聞き取り、`monthly/<YYYY-MM>.md` の評価テーブルを更新する。

## GEPPO 提出文フォーマット

GEPPO の④自由記述はプレーンテキスト。以下の形式で簡潔に（300字前後を目安）:

```text
# <プロジェクト名>
- <成果1行>
- <成果1行>

# 今後の予定
- <予定>
```

- 成果目標・ミッション目標に効くものを優先し、細かい作業は削る
- LT・ハンズオン・スキル配布などの展開活動はミッション目標の証跡なので必ず含める
- ミッション目標セクションは個別発表の羅列でなく、活動の種類で束ねる（例: 「標準化基盤の整備」「開発手法のLT・ハンズオン」「ツール知見の共有」の3行）。LT は当月分だけでなく半期累積で列挙してよい（GEPPO は半期目標に対する進捗報告のため）
- 「今後の予定」は各 projects/ の `## 今後の予定` から集約する

## GEPPO フォーム操作（ブラウザ提出）

提出代行を頼まれたら claude-in-chrome で `https://mbo-geppo.services.isca.jp/main?t=<YYYYMM>` を開く。

- 入力項目: ①②③は天気アイコン5つ（左から S/A/B/C/D）をクリック、④は textarea にプレーンテキスト
- 天気は radio 要素の ref クリックでは反映されないことがある。アイコン画像の座標をクリックし、スクリーンショットで選択色（S=赤、A=オレンジ）を確認する
- セッションタイムアウトは60分。送信時に「エラーが発生しました」が出たら、`/main` に戻ると再ログイン済みで開けるが**フォームはリセットされている**ので①〜④を再入力して再送信する
- 送信完了後も `?t=<YYYYMM>` で再度開けば前回値が入った状態で再編集・再送信できる（月内は上書き可能）
- 送信は不可逆・上司共有のため、クリック前に必ずユーザーへ最終確認する

## ガードレール

- monthly/ を直接手で育てない。projects/ に追記してから生成する
- 半期目標が変わったら `goals/<半期>.md` を新規作成する（既存半期は書き換えない）
- コミットはユーザー確認のうえで行う。push・リモート作成は明示依頼があるときのみ
- 工数（営業日カウント）や Slack 向け上長報告は `work-log-maintenance` の領域。ここでは扱わない
