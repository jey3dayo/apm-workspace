# PR レビューの提出

他人の PR について、指摘を集めて取捨し、GitHub の review として積むまで。指摘の検出は他のスキルが持ち、ここにあるのは、どれを出すか、どう書くか、どう積むかの規則だけ。draft の PR も、自分がレビュアーに assign されていない PR も対象にする。ready 化や assign はしない。

## 1. 対象を固定して指摘を集める

1. `gh pr view <n> -R <owner>/<repo> --json baseRefOid,headRefOid` で base / head の SHA を記録する。以降の確認と投稿はこの SHA に対して行う
2. 指摘を集める。repo 専用のレビュースキルがあればそれ、無ければ実行環境の組み込みレビュー（Claude Code の `/code-review` など）、どちらも無ければ自分で差分を読む。検出側には候補を返すところまでを頼み、GitHub への投稿は本スキルで行う
3. ユーザーと会話で文面を詰めた指摘も、検出の完了を待って同じ候補列に入れる。別の review に分けたり、それだけで止めたりしない

- 完了条件: 記録した SHA に対する検出結果と、会話で固まった指摘が、1つの候補列にそろった

## 2. 取捨する

候補ごとに、出すか外すかを決めて理由を残す。外すのは次のもの。

- PR より前から存在し、今回の変更で発生も悪化もしていない問題。今回の変更が原因なら、未変更の行の問題でも残し、原因になった差分の行に付ける
- 前提を自分で確かめていない指摘。コードを開いて確かめた指摘だけ出す
- 自分の個人規約（global AGENTS.md など）だけが根拠で、repo の規約に無い指摘
- 横断的な課題で、関連 issue（`gh issue list --search`）の方針や対象外の節と矛盾するもの。範囲外ならその issue へ回すと書いて外す
- 同じ根本原因を持つ別の指摘に吸収できるもの。吸収先のコメントで一緒に扱う

残した指摘には **要対応** か **任意** を付ける。

- 完了条件: 全候補に「出す（要対応 / 任意）」か「外す（理由）」が付いた

## 3. 書き換え案を付ける（構造の提案があるとき）

構造の変更を求める要対応の指摘には、文章だけでなく案のコードを付ける。

1. 案を `tmp/<pr>-review/` に書き、趣旨・意図した挙動差分・自分の懸念を同じ場所のメモにまとめる。案は PR の実装ファイルへ適用しない
2. 独立した Reviewer に read-only でレビューさせる。model・経路・verdict の受理条件は `orchestrator-worker`「Reviewer の tier」に従う。依頼には PR の base / head SHA と、案のパスと `shasum` の値を入れ、返ったレビューがその版を対象にしたことを確かめる
3. 要対応の指摘を直して再レビューする。往復は最大3回。残った任意の指摘はメモに記録する

3回で要対応が残ったら、案を投稿せずに止め、残りの指摘をユーザーへ報告する。

- 完了条件: 受理したレビューに要対応が残っていない

## 4. review を組み立てる

### 文面

- 各コメントの先頭に **要対応** / **任意** を書く
- 指摘は常体。構造の提案のように対話を目的とするコメントだけ敬体にする。書いたら指摘側の各コメントの文末を読み、敬体（です・ます・ました・でした・でしょう・ましょう・ください）が残っていないか確かめる。コードや引用の中の語は対象外
- 提案の根拠は、確かめたコード・再現結果・repo の契約にし、関連 issue や公式 docs があれば添える。評価語（「大変」「ベストプラクティス」）は使わない
- 書き換え案は `<details>` で折りたたみ、実行・型検査をしたかを書く
- review 本文には、要対応の件数と所在、書き換え案の検証状況を書く

### 投稿

API の呼び方は [references/github-review-api.md](references/github-review-api.md)。

1. head SHA を取り直す。§1 の記録と違えば、変わった差分について §1〜§3 をやり直し、この §4 の頭から進め直す
2. 自分の pending review が既にあるか確かめる（PR ごとに1つしか持てない）。あれば本文と既存コメントを読み、残すものと今回差し替えるものを決める。削除する前に、本文と残すコメントを `tmp/<pr>-review/` に保存する（UI で編集された本文は消すと戻せない）。review の `commit_id` が現在の head と違えば review ごと削除して現在の head で作り直し、同じなら追記する。無ければ作成する
3. その review のコメントを全件取得し、§2 で出すと決めた指摘と1対1で照合する（path・side・行または範囲・本文全体）。欠落は追記、重複は削除、位置の誤りは削除して付け直す

- 完了条件: 今回の「出す」が review に過不足なく入り、手順 2 で残すと決めた既存コメントが変わらず残り、文面が上の規則どおり

## 5. 提出

依頼の言葉で終わり方が決まる。

| 依頼                                          | 終わり方                                                                                                                       |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 「pending review 作って」など、pending を指定 | PENDING のまま止める。提出はユーザー                                                                                           |
| 「レビュー出して」「投げて」など、提出まで    | head SHA を取り直し、変わっていれば §4 をやり直す。COMMENT で提出する。APPROVE は依頼に「approve」「承認」が明示されたときだけ |

- 完了条件: その review の `state` が依頼どおり（PENDING、または APPROVED / COMMENTED で `submitted_at` あり）であることを取得して確かめ、review の URL・各コメントの場所と要否・外した候補とその理由を報告した
